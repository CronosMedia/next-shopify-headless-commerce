# Audit tehnic si de produs: Next Shopify Headless Commerce

Data auditului: 15 iunie 2026  
Repo analizat: `next-shopify-headless-commerce`  
Branch curent: `luxury-ui`

## 1. Rezumat executiv

Acest proiect nu mai este un starter gol. Are deja o directie vizuala recognoscibila, un numar mare de fluxuri comerciale si suficienta substanta pentru a deveni demo-ul Shopify headless principal al Veridis.

Verdictul meu este:

> Merita continuat si rafinat, dar nu trebuie prezentat inca drept produs gata de productie.

Motivul nu este lipsa de design. Designul este, de fapt, unul dintre punctele bune. Problemele principale sunt:

1. build-ul de productie nu trece;
2. exista o vulnerabilitate critica de autorizare in fluxul de anulare a comenzilor;
3. integrarea Shopify este fragmentata intre mai multe abordari concurente;
4. identitatea demo-ului este incoerenta: fashion luxury, catalog Shopify cu snowboard-uri, texte romanesti, piata UK si monede diferite;
5. SEO, accesibilitatea, observabilitatea si testarea sunt aproape inexistente;
6. multe functionalitati arata complet in UI, dar sunt mock, incomplete sau nu persista.

Proiectul are valoare demonstrativa, insa prima etapa trebuie sa fie consolidarea fundatiei, nu adaugarea altor efecte vizuale.

## 2. Ce exista deja si merita pastrat

Proiectul are aproximativ 12.100 de linii sursa proprii, fara codul GraphQL generat, 21 de pagini App Router, 20 de Route Handlers si 53 de module client.

Functionalitati deja prezente:

- homepage editorial cu hero, campanii, carusel si newsletter;
- lista de colectii;
- pagina de colectie cu sortare si filtre;
- pagina de produs cu galerie, lightbox, selectare variante si sticky buy box;
- cos Shopify;
- checkout redirectionat catre Shopify;
- wishlist in `localStorage`;
- produse vizualizate recent;
- cautare si live search;
- recomandari de produse;
- quick view, partial implementat;
- autentificare client;
- profil, adrese si istoric comenzi;
- detalii comanda si tracking;
- cerere de anulare;
- pagini legale, contact, FAQ, livrare si retur.

Directia vizuala actuala are cateva calitati reale:

- tipografie si spatiere consistente pe homepage, colectii si PDP;
- imagini editoriale bine alese pentru conceptul fashion;
- header transparent pe hero si solid dupa scroll;
- product grid aerisit;
- ierarhie vizuala buna pe desktop;
- un limbaj vizual suficient de diferit de un template Shopify standard.

Acestea sunt active utile. Nu recomand rescrierea proiectului de la zero.

## 4. Constatari critice

### P0. Broken authorization la cererea de anulare

Fisier: `src/app/api/orders/cancel-request/route.ts`

Ruta verifica doar daca exista cookie-ul `customer-access-token`, apoi accepta din browser:

- `orderId`;
- `orderName`;
- `customerEmail`.

Dupa aceea foloseste tokenul Admin API pentru a modifica tag-urile comenzii primite.

Nu se verifica daca acea comanda apartine clientului autentificat.

Consecinta:

> Orice client autentificat care obtine sau ghiceste un GID de comanda poate trimite o cerere care modifica alta comanda din Shopify.

Aceasta este o vulnerabilitate de tip IDOR/BOLA: identificatorul resursei vine de la client, dar serverul nu verifica dreptul utilizatorului asupra resursei.

Remediere:

1. se ignora complet `customerEmail` si `orderName` primite de la browser;
2. se extrage clientul exclusiv din sesiunea server-side;
3. se interogheaza comenzile acelui client;
4. se confirma ca `orderId` solicitat se afla in comenzile lui;
5. abia apoi se apeleaza Admin API;
6. se adauga rate limiting, audit log structurat si protectie contra cererilor repetate.

Cerinta de acceptanta:

- un client nu poate citi sau modifica prin aceasta ruta nicio comanda care nu ii apartine;
- test automat pentru incercarea de acces la comanda altui client.

### P0. Build-ul de productie nu trece

Comanda rulata:

```bash
npm run build
```

Bundle-ul se compileaza, dar build-ul esueaza la TypeScript. Primul blocaj raportat este in `src/app/api/account/route.ts`, unde tipul generic al raspunsului Shopify nu corespunde destructurarii folosite.

Separat, `npx tsc --noEmit --incremental false` raporteaza:

- incompatibilitati ale tipurilor pentru raspunsurile GraphQL;
- prop lipsa in `QuickViewModal`;
- foarte multe identificatoare duplicate in fisierul GraphQL generat;
- rute de cont care presupun forme de date diferite fata de query-uri.

Un demo comercial trebuie sa poata fi construit reproducibil in CI. In acest moment nu poate.

### P0. Cod GraphQL generat corupt sau duplicat

`src/lib/shopify/generated/graphql.ts` are peste 17.000 de linii si contine definitii duplicate ale aceluiasi schema.

Probabila cauza este configurarea codegen:

- preset-ul `client` genereaza deja tipurile necesare;
- sunt adaugate simultan plugin-urile `typescript` si `typescript-operations`;
- directorul de output poate pastra continut generat necuratat;
- scriptul si schema sunt legate de un magazin si o versiune hardcodate.

Remediere:

1. alegerea unei singure strategii de codegen;
2. stergerea controlata si regenerarea directorului;
3. validare in CI prin `npm run codegen && git diff --exit-code`;
4. query-uri tipate, nu wrapper generic cu `any`.

## 5. Securitate si confidentialitate

### P1. Admin API este accesibil prin prea multe trasee

`src/lib/shopify.ts` exporta din acelasi modul:

- clientul Storefront;
- request-ul Storefront autentificat;
- request-ul Admin API.

Modulul este importat si din componente client prin dependente precum `src/lib/cart.ts`.

Chiar daca bundler-ul poate elimina codul server-only nefolosit, aceasta granita nu este explicita. Un import gresit ulterior poate expune sau incerca sa includa logica sensibila.

Recomandare:

- `src/lib/shopify/storefront.server.ts`;
- `src/lib/shopify/admin.server.ts`, cu `import 'server-only'`;
- `src/lib/shopify/types.ts`;
- clientul browser separat doar daca este intentionat.

### P1. Date personale sunt scrise in fisiere de debug

Ruta `src/app/api/account/proxy/orders/[id]/route.ts` foloseste `appendFileSync` si scrie in `proxy-debug.log`:

- email client;
- ID client;
- ID-uri de comenzi;
- raspunsuri Shopify;
- produse, sume, tracking si alte date asociate comenzii.

Probleme:

- PII ramane pe disc fara politica de retentie;
- fisierele log sunt deja urmarite de Git;
- scrierea sincrona blocheaza event loop-ul;
- filesystem-ul local nu este fiabil in serverless;
- raspunsurile complete nu trebuie logate in productie.

Exista si `cancellation-debug.log`, plus multe `console.log`.

Remediere:

- eliminarea logurilor cu payload complet;
- logger structurat cu redactare;
- ID de corelatie;
- niveluri diferite pentru development si production;
- excluderea logurilor din Git si eliminarea lor din istoric daca au continut sensibil.

### P1. Formularul de contact nu trimite nimic

Ruta `src/app/api/contact/route.ts` doar scrie numele, emailul si mesajul in consola, asteapta o secunda si raspunde cu succes.

UI-ul afirma ca mesajul a fost trimis, desi nu a fost.

Pentru un demo promovat public, aceasta este o functionalitate inselatoare si un risc de pierdere a lead-urilor.

Sunt necesare:

- provider real de email;
- validare de schema;
- limita de lungime;
- honeypot/CAPTCHA adaptiv;
- rate limiting;
- mesaj de eroare real;
- acord si informare privind prelucrarea datelor.

### P1. Lipsesc rate limiting si validare robusta

Rute expuse:

- login;
- register;
- contact;
- search;
- cancel request;
- update profil/adrese.

Nu exista un mecanism comun de rate limiting. Validarea este facuta manual si neuniform.

Recomandare:

- schema Zod pentru fiecare payload;
- limite de dimensiune;
- rate limiting pe IP si, unde exista, pe customer ID;
- mesaje publice generice, detalii doar in logurile serverului.

### P1. Sesiunea client necesita consolidare

Cookie-urile sunt `httpOnly`, `secure` in productie si `sameSite: lax`, ceea ce este un inceput bun.

De corectat:

- setarea explicita `path: '/'`;
- stergerea tuturor cookie-urilor asociate la logout;
- expirare coerenta cu tokenul Shopify;
- rotire si tratarea tokenurilor expirate;
- verificarea `Origin` pentru mutatii sensibile;
- un singur modul pentru sesiune.

Dependenta `iron-session` este instalata, dar nu este folosita.

### P1. Customer Accounts foloseste modelul legacy

Implementarea se bazeaza pe `customerAccessToken` din Storefront API.

Aceasta poate functiona pentru conturile clasice, dar arhitectura trebuie aleasa explicit:

- conturi clasice si mentinerea fluxului actual; sau
- Customer Account API cu OAuth 2.0 si modelul nou de conturi Shopify.

Nu recomand migrarea mecanica doar fiindca API-ul nou exista. Pentru demo trebuie documentat ce tip de cont Shopify este suportat, ce functionalitati ofera si care sunt compromisurile.

## 6. Integrarea Shopify

### P1. Sunt doua arhitecturi de cart

Exista:

- operatii de cart executate direct din browser prin `CartProvider -> src/lib/cart.ts`;
- Route Handler separat la `/api/cart`.

Aceasta duplicare produce doua surse de adevar si face dificila adaugarea ulterioara a:

- validarii;
- observabilitatii;
- market/country context;
- discounturilor;
- extensiilor B2B;
- logicii de merchandising.

Trebuie aleasa o singura strategie.

Pentru acest demo recomand un BFF subtire in Next Route Handlers sau Server Actions pentru mutatii, iar Storefront API sa ramana server-side. Avantajul este controlul si posibilitatea de a explica arhitectura intr-un studiu de caz Veridis.

### P1. Se creeaza cart chiar si fara intentie de cumparare

La montarea globala a `CartProvider`, `ensureCart()` creeaza un cart nou daca nu exista `cartId`.

Astfel, fiecare vizitator poate genera un cart Shopify doar prin deschiderea site-ului.

Mai bine:

- se citeste cart-ul doar daca exista ID;
- primul cart se creeaza la primul `addToCart`;
- cart ID se tine intr-un cookie securizat sau intr-un mecanism controlat, nu doar in `localStorage`.

### P1. Selectarea metodei de livrare este afisata, dar nu implementata

Provider-ul expune `setSelectedDeliveryOption`, iar UI-ul permite alegerea metodei. Mutatia Shopify corespunzatoare este comentata/neimplementata.

O functionalitate care arata activa, dar nu modifica backend-ul, trebuie fie finalizata, fie scoasa temporar din UI.

### P1. Rutele pentru cont si comenzi sunt duplicate

Exemple:

- `/api/account` si `/api/account/update`;
- `/api/account/orders/[id]` si `/api/account/proxy/orders/[id]`;
- doua metode diferite de initializare a clientului Shopify;
- forme diferite de raspuns pentru aceeasi entitate.

Ruta non-proxy de detaliu comanda pare incompatibila cu query-ul folosit:

- trimite `orderId`;
- query-ul asteapta `customerAccessToken` si `first`;
- codul asteapta `response.data.node`;
- query-ul returneaza `customer.orders`.

Aceasta ruta trebuie considerata defecta pana la proba contrarie.

### P1. Versiunile API sunt vechi si hardcodate

Fallback-ul este `2024-10`, iar `codegen.ts` foloseste direct aceeasi versiune si un shop domain hardcodat.

Versiunile Shopify sunt versionate trimestrial si au o perioada limitata de suport. Versiunea trebuie:

- centralizata;
- configurata prin env;
- actualizata planificat;
- testata inainte de expirare;
- folosita identic la runtime si codegen.

### P2. Tokenul public este hardcodat in scriptul npm

Storefront access token-ul public nu este echivalentul unui Admin token secret, dar nu trebuie hardcodat in `package.json`.

Problemele sunt portabilitatea, rotirea si configurarea pe medii, nu secretul in sine.

Scriptul trebuie sa citeasca env-ul existent. Domeniul magazinului trebuie si el configurabil.

### P2. Tipurile Shopify sunt definite de mai multe ori

Tipurile `Cart` si structurile asociate exista atat in `src/lib/shopify.ts`, cat si in `src/lib/cart.ts`, pe langa tipurile generate.

Aceasta produce drift: de exemplu `country` versus `countryCode`, `province` versus `provinceCode`.

O singura sursa de tipuri reduce bug-urile si face codul mai usor de invatat.

## 7. Catalog, colectii si cautare

### P1. Filtrele opereaza doar pe primele produse incarcate

Query-ul colectiei aduce un numar limitat de produse, iar filtrele sunt aplicate in browser numai peste acel subset.

Consecinte:

- numarul de produse este incomplet;
- brandurile si tag-urile disponibile sunt incomplete;
- filtrarea poate spune „0 rezultate” desi Shopify are produse potrivite;
- nu exista paginare sau load more;
- filtrele nu sunt shareable prin URL.

Solutia corecta:

- Shopify Search & Discovery filters;
- filtre trimise in Storefront API;
- cursor pagination;
- starea filtrelor in URL;
- loading si empty states controlate.

### P1. Calculul intervalului de pret este gresit

Codul foloseste:

```ts
Math.min(...prices, 0)
Math.max(...prices, 1000)
```

Rezultatul forteaza minimul la cel mult zero si maximul la cel putin 1000, indiferent de catalog.

In captura auditului, filtrul de pret era deja activ automat intre `£600` si `£1025`, desi utilizatorul nu il activase constient.

### P2. Sortarea este in URL, restul filtrelor nu

Aceasta produce comportament inconsistent:

- sortarea supravietuieste refresh-ului;
- filtrele dispar;
- back/forward nu reface starea;
- linkul nu poate fi distribuit.

### P2. Live search-ul are accesibilitate si trafic necontrolat

Exista debounce, ceea ce este bine, dar lipsesc:

- anularea requestului anterior cu `AbortController`;
- roluri combobox/listbox;
- navigare cu sageti;
- anuntarea rezultatelor pentru screen reader;
- stare „no results”;
- cache;
- rate limiting.

## 8. Product Detail Page

### P1. Acces direct la `window` in timpul renderului

`ProductView.tsx` calculeaza:

```ts
window.matchMedia('(min-width: 1024px)').matches
```

direct in JSX.

Un Client Component este tot pre-randat pe server. `window` nu exista pe server, deci aceasta expresie poate produce eroare la SSR sau hidratare.

Trebuie folosita o stare derivata intr-un effect sau, preferabil, CSS responsive.

### P1. Varianta selectata si sticky buy box-ul nu sunt sincronizate

Sticky buy box primeste mereu `firstVariant`, nu varianta aleasa in BuyBox.

Un utilizator poate selecta o alta marime/culoare, dar bara sticky poate adauga prima varianta.

Starea variantei trebuie ridicata in `ProductView` si folosita de ambele componente.

### P1. Combinatiile de optiuni pot deveni invalide

Selectarea unei valori cauta variante dupa cate o optiune, fara un model robust pentru matricea completa de optiuni.

Pentru produse cu mai multe axe, de exemplu culoare si marime, UI-ul poate lasa selectata o combinatie inexistenta.

### P1. Recomandarile sunt cerute de doua ori

Pagina server fetch-uieste `relatedProducts` si le trimite ca prop. `ProductView` nu foloseste prop-ul si monteaza `RelatedProducts`, care face alta cerere.

Rezultat:

- request Shopify inutil;
- payload RSC mai mare;
- cod mai greu de urmarit.

### P1. Continut comercial fictiv este prezentat ca adevar

Pentru orice produs apar afirmatii precum:

- produs realizat manual in serii limitate;
- materiale 100% reciclate;
- garantie de doi ani;
- livrare gratuita peste un prag;
- recenzii si cumparatori verificati.

Acestea sunt date mock, nu informatii din Shopify.

Pentru demo trebuie etichetate clar ca mock in development sau alimentate din:

- metafields;
- metaobjects;
- app de reviews;
- configuratie de shop.

Altfel demo-ul invata un pattern gresit: continutul comercial nu trebuie inventat in componenta.

### P2. Lipseste URL-ul variantei

Varianta aleasa nu este reflectata in URL. Linkurile nu pot deschide direct configuratia aleasa, iar refresh-ul o pierde.

### P2. Galerie/PDP fragil la continut real

In captura headless a PDP-ului, zona media din stanga nu era vizibila in primul viewport, iar continutul textual ocupa un layout dezechilibrat.

Trebuie testate:

- produs fara imagine;
- o singura imagine;
- imagini cu rapoarte diferite;
- produs cu o varianta;
- produs cu zeci de variante;
- sold out;
- pret promotional;
- descriere foarte lunga sau goala.

## 9. Continut si pozitionare

### P1. Demo-ul nu are inca o poveste unitara

Homepage-ul spune:

- fashion luxury;
- Mayfair si Savile Row;
- materiale si croitorie;
- „MAISON”.

Catalogul Shopify afiseaza:

- snowboard-uri;
- produse Hydrogen demo;
- gift cards;
- produse de test.

Pagini secundare spun:

- Bucuresti si Romania;
- preturi in LEI;
- texte in romana.

Footer-ul spune:

- United Kingdom / English;
- adresa fictiva din Londra.

Aceasta este cea mai importanta decizie de produs, dupa remedierea P0.

Recomandarea mea:

> Nu construi un brand luxury fictiv complet. Construieste un demo vertical credibil, cu date coerente si functionalitati care arata valoarea headless.

Nise bune pentru demo:

1. fashion premium accesibil;
2. skincare/cosmetics;
3. home decor;
4. specialty food sau coffee;
5. sports/outdoor premium, daca pastram catalogul de snowboard.

Fashion este potrivit pentru designul actual, dar necesita un seed catalog coerent: produse, variante, marimi, materiale, imagini, politici si moneda.

### P1. Piata, limba si moneda trebuie alese

Acum sunt amestecate:

- engleza;
- romana;
- GBP;
- RON/LEI;
- Romania;
- United Kingdom.

Pentru un demo Veridis destinat pietei romanesti recomand:

- interfata principala in romana;
- RON prin `Intl.NumberFormat`;
- continut optional in engleza ca demo de internationalizare;
- Shopify Markets documentat;
- fara simbol valutar hardcodat.

Alternativ, demo-ul poate fi international in engleza, dar atunci toate paginile trebuie aliniate.

### P2. Linkuri si informatii placeholder

Exista linkuri catre rute inexistente, precum:

- `/brand-promise`;
- `/careers`;
- `/plati-sigure`.

Linkurile sociale duc la `#`.

Footer-ul afiseaza `© 2024`, iar datele de contact sunt placeholder.

## 10. SEO

### P1. Metadata este generica

Exista doar metadata globala:

- titlu `Next Commerce`;
- descriere generica.

Lipsesc:

- `generateMetadata` pentru produse si colectii;
- canonical;
- Open Graph;
- Twitter cards;
- imagine sociala;
- `robots.ts`;
- `sitemap.ts`;
- Product JSON-LD;
- Organization/WebSite JSON-LD;
- breadcrumb structured data;
- `noindex` pentru cautari si zone private, unde este cazul.

### P1. Semantic heading incorect

Logo-ul din header este un `<h1>` pe fiecare pagina.

PDP-ul si colectia au deja propriul `<h1>`, rezultand o ierarhie gresita. Wordmark-ul trebuie sa fie `span` sau element neutru.

### P2. Descrierile Shopify sunt subutilizate

Colectiile nu afiseaza descrierea sau imaginea in mod util pentru continut si SEO.

## 11. Accesibilitate

### P1. Mega menu este practic hover-only

Butonul nu are comportament complet pentru:

- click;
- Enter/Space;
- Escape;
- `aria-expanded`;
- `aria-controls`;
- focus management.

Pe tastatura si touch, navigatia nu este robusta.

### P1. Search overlay nu este un dialog accesibil

Lipsesc:

- eticheta accesibila explicita;
- buton clar de inchidere;
- Escape;
- focus trap unde este necesar;
- returnarea focusului;
- rolurile pentru sugestii.

### P1. Butoanele cu icon au etichete insuficiente

Multe folosesc doar `title`, iar butonul de meniu mobil nu are `aria-label` sau `aria-expanded`.

### P2. Motion nu respecta `prefers-reduced-motion`

Homepage-ul foloseste:

- parallax la scroll;
- tranzitii de doua secunde;
- smooth scrolling global;
- zoom pe imagini.

Trebuie oferita varianta redusa pentru utilizatorii care o solicita.

### P2. Focus styles si contrastele trebuie auditate

Textul foarte subtire si gri deschis peste imagini sau fundaluri poate cobori sub contrastul necesar. Este nevoie de axe/Lighthouse plus verificare manuala.

## 12. Performanta

### P1. Prea mult JavaScript global

Root layout monteaza global mai multi provideri client:

- auth;
- UI;
- cart;
- wishlist;
- smooth scroll;
- quick view;
- header interactiv.

Consecinta este hidratarea unui volum mare de JS pe fiecare pagina, inclusiv pagini legale.

Trebuie masurat bundle-ul si mutate granitele client cat mai jos.

### P1. Header-ul face request-uri duplicate

Sunt randate doua instante `MegaMenu`, iar fiecare face propriul request la `/api/collections`.

Colectiile pot fi:

- aduse o data in Server Component;
- transmise ambelor meniuri;
- cache-uite cu revalidare.

### P1. Strategia de cache nu este definita

O parte din request-uri folosesc clientul SDK, altele raw fetch cu `no-store`.

Nu exista o politica explicita pentru:

- catalog;
- colectii;
- produs;
- recommendations;
- search;
- cart;
- customer data.

Recomandare:

- catalog public: cache si revalidare;
- search: cache scurt sau no-store controlat;
- cart/cont: no-store;
- webhooks sau revalidation pentru actualizari.

### P2. Parallax-ul actualizeaza state la fiecare scroll

`HeroSection` seteaza React state pentru fiecare eveniment de scroll. Aceasta poate produce multe rerender-uri.

Pentru efecte simple:

- CSS;
- requestAnimationFrame;
- motion value;
- sau eliminarea efectului pe dispozitive slabe.

### P2. Imaginile hero sunt servite la calitate 100

`quality={100}` nu este automat sinonim cu perceptie mai buna. Trebuie masurat LCP si folosite dimensiuni/quality adaptate.

### P2. Dependente nefolosite si artefacte

- `iron-session` pare nefolosit;
- componente/importuri si cod quick-add nefolosite;
- fisier `.bak`;
- loguri;
- configuratie `.idea`;
- `.next` local are aproximativ 375 MB.

## 13. Calitatea codului

### P1. Lint-ul are 122 de erori si 5 warnings

Comanda:

```bash
npm run lint
```

Rezultat:

- 127 probleme;
- 122 errors;
- 5 warnings.

Categorii principale:

- `any`;
- importuri si variabile nefolosite;
- hook dependencies;
- caractere neescape-uite;
- optional chaining urmat de non-null assertion.

### P1. Componente foarte mari

Exemple:

- `src/app/account/page.tsx`: aproximativ 1.200 linii;
- `CollectionProductGrid.tsx`: aproximativ 700;
- cart page: peste 500;
- `AddressModal.tsx`: peste 400;
- order detail: peste 400;
- `CartProvider.tsx`: aproape 500.

Marimea nu este o problema singura. Problema este amestecul de:

- fetching;
- transformare de date;
- state;
- validare;
- markup;
- business rules;
- debugging.

Pentru invatare, refactorizarea trebuie facuta pe responsabilitati, nu doar taiata arbitrar in fisiere mici.

### P1. ESLint si Next au versiuni majore diferite

- Next: `16.1.6`;
- `eslint-config-next`: `15.1.0`.

Acestea trebuie aliniate pentru reguli si compatibilitate predictibile.

### P2. README-ul nu documenteaza proiectul

## 15. Hosting

Acest Next.js storefront poate fi gazduit fara Oxygen:

- Vercel;
- Netlify;
- VPS Hetzner;
- Docker pe orice provider compatibil Node;
- platforme precum Fly.io sau Render.

Pentru demo-ul Veridis:

- Vercel simplifica preview deployments si prezentarea;
- Hetzner ofera control si cost predictibil, dar necesita reverse proxy, TLS, deploy, procese, loguri si monitoring;
- Docker mentine portabilitatea.

Shopify ramane providerul de commerce si checkout. Hosting-ul frontendului nu cere Shopify Plus.

## 17. Roadmap recomandat

Estimarea este orientativa pentru lucru atent, inclusiv explicatii si invatare.

### Faza 0: Safety gate

Durata: 1-2 zile

- remediere autorizare cancel request;
- eliminare logging PII;
- protejare explicita a modulului Admin API ca server-only;
- eliminare token hardcodat din script;
- inventar si rotire pentru orice credential sensibil;
- formularele mock marcate sau dezactivate.

Definitia de gata:

- nu exista ruta care modifica o comanda fara ownership check;
- logurile nu contin payload-uri personale;
- Admin token nu poate ajunge intr-un client bundle.

### Faza 1: Build verde

Durata: 2-4 zile

- reparare codegen;
- tipare corecta pentru request-uri;
- eliminare rute duplicate defecte;
- aliniere Next/ESLint;
- rezolvare lint;
- scripturi `typecheck` si `check`;
- CI pe pull request.

Definitia de gata:

```bash
npm run lint
npm run typecheck
npm run build
```

toate ies cu cod 0.

### Faza 2: Arhitectura Shopify coerenta

Durata: 4-7 zile

- separare Storefront/Admin;
- alegere strategie unica pentru cart;
- lazy cart creation;
- modele tipate comune;
- strategie de cache;
- un singur traseu pentru account/orders;
- decizie Customer Account API versus classic accounts;
- finalizare delivery option sau eliminare UI.

Definitia de gata:

- fiecare domeniu are o singura sursa de adevar;
- nu exista query-uri duplicate pentru acelasi flux;
- document de arhitectura scurt.

### Faza 3: Identitate si date demo

Durata: 3-6 zile

- alegere nisa, limba, piata si moneda;
- catalog seed coerent;
- eliminare continut fictiv nejustificat;
- metafields/metaobjects pentru continut;
- linkuri, contacte si politici consistente;
- sistem central de formatare bani.

Definitia de gata:

- nicio pagina nu amesteca Romania, UK, GBP si RON;
- fiecare afirmatie comerciala vine din date sau configuratie.

### Faza 4: Commerce UX

Durata: 5-8 zile

- filtre Shopify server-side;
- URL state;
- cursor pagination;
- variante valide si URL de varianta;
- sincronizare sticky buy box;
- cart optimistic si error recovery;
- cautare accesibila;
- recommendations reale;
- empty/loading/error states.

Definitia de gata:

- fluxurile principale functioneaza pe mobile si desktop;
- catalogul mare nu produce filtre false.

### Faza 5: SEO, accesibilitate si performanta

Durata: 4-7 zile

- metadata dinamica;
- JSON-LD;
- sitemap si robots;
- corectare headings;
- mega menu/search accesibile;
- `prefers-reduced-motion`;
- reducere JS global;
- cache si imagine optimization;
- audit Lighthouse si axe.

Tinte orientative:

- Lighthouse Performance: peste 90 pe paginile principale, in conditii controlate;
- Accessibility: peste 95;
- SEO: peste 95;
- fara erori axe critice/serioase;
- Core Web Vitals in pragurile „good” pe deployment real.

### Faza 6: Testare si produs demonstrabil

Durata: 4-6 zile

- Playwright pentru traseele critice;
- teste de autorizare;
- analytics si Web Vitals;
- error tracking;
- README complet;
- pagina de case study;
- deploy preview si production;
- checklist de demo.

Definitia de gata:

- demo-ul poate fi prezentat repetabil fara interventii manuale;
- erorile critice sunt detectate in CI;
- un alt developer poate porni proiectul doar din documentatie.

## 18. Ordinea concreta a urmatoarelor lucrari

Nu recomand sa incepem cu redesign.

Ordinea optima:

1. inchidem vulnerabilitatea de anulare;
2. facem build-ul verde;
3. curatam codegen si tipurile Shopify;
4. unificam cart si account API;
5. alegem nisa, piata si moneda;
6. inlocuim catalogul demo;
7. refacem PLP/PDP pe date reale;
8. SEO, a11y si performanta;
9. teste si deploy;
10. abia apoi finisaj vizual final.

## 19. Cum lucram ca sa inveti prin proiect

Pentru fiecare etapa recomand acelasi ciclu:

1. explicam problema si efectul ei;
2. desenam fluxul de date;
3. scriem un test sau un criteriu verificabil;
4. implementam cea mai mica schimbare corecta;
5. verificam in browser si CLI;
6. documentam decizia.

Exemplu pentru vulnerabilitatea de anulare:

- autentificarea raspunde la „cine esti?”;
- autorizarea raspunde la „ai voie sa modifici aceasta comanda?”;
- prezenta cookie-ului rezolva doar prima intrebare;
- ownership check rezolva a doua intrebare.

Acest tip de distinctie este mai valoros pe termen lung decat memorarea unei anumite functii Shopify.

## 22. Concluzie

Acest repo este alegerea mai buna pentru demo-ul Shopify headless Veridis decat pornirea unei alte implementari de la zero.

Are deja suficienta expresivitate vizuala si functionalitate pentru a arata potentialul unui storefront headless. Totusi, valoarea lui comerciala va veni din incredere: build reproducibil, securitate, date reale, fluxuri robuste si o poveste coerenta.

Designul nu este problema principala. Fundatia tehnica si identitatea demo-ului sunt.

Prima tinta recomandata este un milestone scurt numit:

> Foundation Green: secure, typed, buildable.

Dupa acel milestone putem investi cu incredere in catalog, UX si prezentarea publica.
